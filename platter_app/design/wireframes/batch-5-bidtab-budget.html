Bid tab & budget

Priority #3 (D-07): where invited bids become a leveled comparison and a working budget. This batch also carries the two obligations flagged at the end of Batch 4, plus a fifth screen added beyond the original index — see below.

⚠E-13→E-19 stays unresolved, but it's load-bearing here. A sub's real price now sits on screen next to a GC plug. Rather than inventing the abandoned field-level redaction model, this batch adds one narrow, explicit decision (D-38): a coarse presentation mode that masks all bid amounts at once when screen-sharing. It is not per-field, not permission-based, and not a substitute for the real spec if one ever gets written.
🧩E-33 lands here. 5.1 now has a dedicated review queue for bid lines a sub added that don't match any scope_line_item — the obligation flagged at the close of Batch 4.
⚙5.5 is new — not in the original STEP1_PLAN.md index. Per owner direction to make the bid tab and budget genuinely user-configurable — plug rules, flag thresholds, custom columns — without needing new code for every tweak. It's a rule builder and a custom-column library, both plain dropdowns and formulas, no code. Logged as D-41.

Every slider recalculates both scenarios live. Energy escalation is split out from the general rate on purpose — it's the input most likely to flip which column wins. Saving a tuned assumption set as a reusable default happens in Automation & customization (5.5).

  1. 1Opting in is per-system, and comparison is optional per system. Not every system has a real alternative worth pricing out — TPO here just tracks its own lifecycle cost, no second column forced on it.
  2. 2Data entry is scenario-shaped, not system-shaped (D-43). A system with an alternate under evaluation gets two rows sharing one set of fields — initial cost, service life, replacement cost, maintenance, energy cost, salvage value — so the comparison is native to the table, not bolted on after.
  1. 3Research now also proposes the alternate's case, not just the baseline's — an energy-savings claim is exactly the kind of number worth a citation and a confidence dot rather than a bare percentage.
  2. 4The result is a comparison, not a number — this is the actual payoff of D-43's scenario model. Splitting energy escalation from general escalation is what lets a pricier, more efficient option's advantage compound correctly over the analysis period instead of being averaged away.

Q-16 — closed, S13 → D-43. Lifecycle cost analysis is scenario-based: lifecycle_scenario (not a flat lifecycle_line), keyed to a system with a baseline and, optionally, one or more alternates. Energy cost and its own escalation rate are first-class fields, not folded into general maintenance or the project-wide escalation assumption — those are the two numbers most likely to actually change an owner's decision, which was the owner's explicit bar for this schema.

What Batch 5 commits us to. The bid tab's source-badge vocabulary (sub / parsed / plug / GC estimate) is now the fixed language for bid_line.source everywhere it's rendered. Sub-added lines resolve into real scope_line_item rows or stay explicitly tracked-only — never silently blended, closing the E-33 obligation. D-38's presentation mode is deliberately narrow; if field-level privacy ever gets specced for real, it sits alongside this toggle, not instead of it. And 5.5 sets a pattern the rest of the app should probably follow: anywhere a number is computed by a rule (a plug, a flag threshold, a custom column), the rule itself should be visible and editable in the same place, not hidden in code — Batch 6's Settings should inherit this shape for flags, trades, and package templates rather than inventing a new one.
