  1. 1Fields grouped by what they're for — identity, dates, requirements, packages — not by which document they came from. The user is verifying a project, not auditing a file.
  2. 2Source pane is permanent, not a modal. Selecting a field scrolls to the page and highlights the bounding box. Verification becomes a glance instead of a document hunt. This is the single most important interaction in Batch 1.
  3. 3Keyboard-first. J/K/Enter clears two dozen fields in under a minute. Mouse works, but the fast path is the one an estimator will actually use twice a week.
  4. 4Confidence is shown as a number, not a vibe. Sea green ≥0.90, apricot 0.70–0.89, grapefruit <0.70. Low-confidence rows expand inline with Confirm / Edit / Reject rather than hiding actions behind a click.
  1. 5Conflicts are resolved by date, proposed not decided. Addenda supersede base documents — the app knows that and says why, but the user chooses. Both sources stay attached, so the history survives.
  2. 6"Not found" names where it looked. That's what makes the absence trustworthy. "Not applicable" is a recordable answer, so nothing sits blank and ambiguous forever.
  3. 7Packages are proposed with their spec sections attached and can be merged or split before acceptance. Accepting one provisions its folder and seeds its scope worksheet — this is the handoff into Batch 3.

E-04 / E-07: flags are a controlled vocabulary (Batch 2 §2.3), and parsing has to respect the same boundary. "Schedule required" is detected and confirmed normally because it's in the library. "Local vendor preference" is not — it surfaces as an unmatched item rather than silently minting a new flag or silently dropping a real requirement, with a one-click path to define it in Settings.

The design bet on this screen: confidence scores alone don't build trust — traceability does. A user won't learn to trust a number, but they will learn to trust a tool that can always show them the sentence it read. Everything else here is in service of making that one gesture instant.

Why this file exists

Requested in the file structure: a clean, readable summary usable across apps without opening the source documents.

It regenerates whenever a confirmed field changes, and keeps prior revisions. Unresolved fields appear honestly as not found rather than being silently omitted.

It's also the cheapest insurance in the build: if Platter is ever set aside, the parse work survives as plain markdown that anyone can read.

Rules these follow: state what happened in plain terms, state what it affects, offer the recovery. No apologies, no error codes, no vague "something went wrong." The user can always proceed manually — parsing is an accelerator, never a gate.

/ Type a command
  1. 1Degraded is offered before failed. OCR with disclosed lower confidence beats refusing the file.
  2. 2Partial results are kept and resumable. Naming which divisions were missed tells the user exactly what they're exposed to.
  1. 3Total failure still creates a project. Manual entry is always the floor. If parsing can gate project creation, one bad afternoon teaches the user not to rely on the tool at all.

What Batch 1 commits us to. Three things carry forward into every later batch: the source-highlight pane becomes the universal "where did this come from" gesture, reused for parsed sub quotes in the bid tab; confidence dots and the extracted_field states become the standard vocabulary for anything AI-derived; and SharePoint write-back starts here, at folder provisioning, rather than being bolted on at step 7.
